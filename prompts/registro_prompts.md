# Registro de prompts

Este anexo resume los prompts relevantes utilizados durante el desarrollo del proyecto. Se registran tanto prompts de generacion y modelado como prompts de revision, depuracion y consolidacion documental, siguiendo el orden aproximado de trabajo del equipo.

| Numero | Parte | Objetivo del prompt | Herramienta/modelo | Resultado obtenido | Ajustes realizados |
| ---: | --- | --- | --- | --- | --- |
| 1 | Planteamiento del caso | Proponer una empresa ficticia de retail omnicanal que permita analizar ventas, clientes, productos, promociones, abandono, segmentacion, asociacion y pronostico. | ChatGPT | Se definio el contexto base de una empresa retail ficticia tipo AndesMarket, con clientes identificables, programa de fidelizacion y ventas transaccionales. | El equipo adapto el caso al alcance del curso y mantuvo el uso de datos sinteticos. |
| 2 | Modelo dimensional | Disenar un esquema estrella para ventas retail con dimensiones de cliente, producto, tienda, tiempo y promocion, indicando el grano de la tabla de hechos. | Claude + revision del equipo | Se obtuvo una propuesta de datamart con `fact_ventas` y dimensiones asociadas. | Se ajustaron nombres de campos y claves para alinearlos con los CSV generados. |
| 3 | Generacion de datos | Solicitar una estrategia para generar datos sinteticos reproducibles con semilla fija, volumen suficiente y reglas de realismo comercial. | ChatGPT + Python | Se definieron criterios de volumen, estacionalidad, clientes frecuentes/esporadicos, promociones y afinidad de productos. | La generacion final se trabajo mediante scripts y tablas maestras del repositorio. |
| 4 | Calidad de datos | Pedir ejemplos de problemas de calidad controlados que puedan introducirse en datos sinteticos de retail para luego ser tratados en ETL. | Claude | Se identificaron problemas como nulos, duplicados, formatos de fecha, inconsistencias textuales y valores extremos. | En la entrega se priorizo la version procesada disponible en `data/processed/`. |
| 5 | Validacion de datos | Verificar si las tablas generadas tienen coherencia entre dimensiones y hechos, claves validas, fechas dentro del rango y metricas basicas consistentes. | Codex + Python | Se reviso la existencia de tablas principales y resultados de validacion del dataset. | Se usaron los scripts de validacion y exploracion como evidencia tecnica. |
| 6 | Datamart ETL | Revisar el notebook de datamart para confirmar si carga las tablas, estandariza campos, valida relaciones y deja el modelo listo para Power BI. | Codex | Se confirmo que `01_datamart_etl.ipynb` trabaja con tablas de `data/processed/` y documenta el datamart. | Se referencio el diccionario de datos como evidencia del modelo. |
| 7 | Diccionario de datos | Generar o completar un diccionario de datos claro para explicar tablas, campos, claves y uso analitico del datamart. | Claude + revision manual | Se consolido la documentacion tecnica en `docs/diccionario_datos.md`. | Se mantuvieron nombres consistentes con las tablas reales del repositorio. |
| 8 | Visualizacion Python | Crear visualizaciones exploratorias que ayuden a interpretar ventas por mes, categoria, productos principales y comportamiento general del negocio. | Gemini + Python | Se generaron graficos exportados en `informe/img/`, como ventas mensuales, categorias, Pareto y mapa de calor. | Se seleccionaron solo visualizaciones utiles para el informe y Power BI. |
| 9 | Revision de Power BI | Verificar si el archivo de Power BI funciona y de donde toma los datos, considerando que el modelo puede tener datos importados y origenes CSV. | Codex | Se confirmo que `powerbi/RetailBI.pbix` contiene un modelo de datos importado y que probablemente se alimenta de CSV procesados. | Se recomendo validar rutas desde Power Query al refrescar en otra maquina. |
| 10 | Clasificacion | Disenar un modelo para identificar clientes con riesgo de abandono usando variables derivadas del comportamiento de compra. | Gemini + Python (scikit-learn) | Se implemento comparacion de Regresion Logistica, Arbol de Decision y Random Forest. | Se definio abandono a partir de recencia y se exporto `predicciones_abandono.csv`. |
| 11 | Revision de clasificacion | Revisar si el notebook de clasificacion tenia nombre consistente con la guia del proyecto y si podia romper el flujo al renombrarlo. | Codex | Se detecto que el archivo estaba como `03_clasificacion_ipynb.ipynb`, distinto al README y a la guia. | Se renombro a `03_clasificacion.ipynb` y se actualizaron referencias en el informe. |
| 12 | Segmentacion | Calcular variables RFM, escalar datos, aplicar K-Means y perfilar grupos de clientes para estrategias diferenciadas. | Gemini + Python (scikit-learn) | Se generaron cuatro segmentos comerciales y se exporto `segmentos_clientes.csv`. | Se ajustaron nombres de segmentos para facilitar la interpretacion de negocio. |
| 13 | Asociacion | Construir transacciones por boleta y aplicar FP-Growth para encontrar reglas de canasta de mercado con soporte, confianza y lift. | ChatGPT + Python (mlxtend) | Se generaron reglas de asociacion exportadas en `reglas_asociacion.csv`. | Se trabajo a nivel de categoria para obtener reglas mas interpretables. |
| 14 | Regresion | Crear un modelo de pronostico de ventas respetando el orden temporal y comparando modelos de regresion. | Gemini + Python (scikit-learn) | Se compararon Regresion Lineal, Random Forest y Gradient Boosting con metricas MAE, RMSE, MAPE y R2. | Se selecciono Gradient Boosting como modelo de referencia para el informe. |
| 15 | Integracion analitica | Verificar que los CSV generados por clasificacion, segmentacion, asociacion y regresion existan y puedan alimentar Power BI. | Codex | Se confirmo la existencia de `predicciones_abandono.csv`, `segmentos_clientes.csv`, `reglas_asociacion.csv` y `pronostico_ventas.csv`. | Se incluyeron estos archivos como evidencias del flujo analitico. |
| 16 | Interpretacion empresarial | Traducir los resultados tecnicos de los notebooks a hallazgos, implicancias de negocio y recomendaciones accionables. | Claude + Codex | Se redactaron interpretaciones para abandono, segmentos, canasta de mercado y pronostico. | Se evitaron conclusiones no sustentadas y se marcaron puntos pendientes cuando correspondia. |
| 17 | KPI e indicadores | Definir KPI principales del proyecto, su formula general, utilidad empresarial y relacion con las partes del proyecto. | ChatGPT + Codex | Se organizaron indicadores como ventas, margen, ticket, riesgo de abandono, segmentos, lift y error de pronostico. | Se usaron valores disponibles en los datos y notebooks existentes. |
| 18 | Informe consolidado | Unificar la documentacion en un solo informe formal siguiendo la estructura indicada por el profesor. | Codex | Se creo y actualizo `informe/Informe_PG_AndesMarket.md` con caratula, resumen, partes tecnicas, etica, conclusiones y contribuciones. | Se eliminaron markdowns separados del informe para trabajar con un documento consolidado. |
